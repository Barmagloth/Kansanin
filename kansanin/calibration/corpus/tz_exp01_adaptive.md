ТЗ: Эксперимент 0.1 — Adaptive refinement на 2D поле (grid+mask)
0) Цель

Проверить гипотезу:

Если вычислять уточнение (refinement) только в активных регионах, выбранных по локальной ошибке ρ, то при фиксированном вычислительном бюджете качество будет не хуже (или лучше), чем у baseline “считаем везде”.
Альтернатива: при фиксированном качестве вычислительный бюджет будет меньше.

Если устойчивого выигрыша нет — эксперимент считается проваленным.

Контекст из плана работ: на этом уровне деревья/октодеревья не нужны; нужен fixed grid + mask + метрики.

1) Определения (чтобы не гадать)
1.1. 2D поле “ground truth”

GT(x,y) — эталонная скалярная карта размера H×W (например 512×512), значения float32.

Поле должно содержать:

Гладкие компоненты: сумма нескольких 2D гауссиан (разные амплитуды/сигмы/центры).

Резкие границы: хотя бы 1–2 фигуры с жёстким порогом (прямоугольник/круг/полоса), чтобы были “edges”.

Пустота: большие области, где значение ≈ 0 (или константа), чтобы было что не считать.

Нужна генерация по seed, чтобы воспроизводимо.

1.2. Coarse vs Refined

Мы моделируем ситуацию “сначала грубо, потом уточняем”.

coarse(GT) — грубая аппроксимация (дешёвая).

refine(coarse, mask) — уточнение только в ячейках, где mask==1 (дорогая часть).

Важно: “дорогость” измеряем через число вызовов refine на ячейку (или тайл), а не через время CPU (время тоже логируем, но бюджет — дискретный, чтобы не зависеть от ноутбука).

1.3. Локальная ошибка ρ

ρ(i,j) — ошибка на ячейке (tile) i,j. Используется для выбора активных регионов.

Два допустимых варианта (реализовать оба, как режимы):

ρ по реконструкции: MSE(GT_tile, coarse_tile)

ρ по “интересности” без GT (опционально): энергия градиента/высоких частот coarse (на случай будущего, но для 0.1 можно не включать).

Для 0.1 обязателен первый вариант (с GT), чтобы не устраивать религиозные войны о детекторе.

2) Модель вычислений (простая, но честная)

Нужно намеренно сделать вычисления “refine” более дорогими, чем “coarse”.

2.1. Разбиение на тайлы

Разбить поле на фиксированную сетку тайлов T×T (например 16×16 или 32×32 пикселя).
Индексируем тайлы: tile_id = (ty, tx).

2.2. Baseline “dense”

Сначала считаем coarse для всего поля.

Затем считаем refine для всех тайлов (или для K тайлов, если бюджет фиксируем одинаково).

2.3. Adaptive “masked”

Сначала считаем coarse для всего поля.

Считаем ρ для всех тайлов.

Выбираем top-K тайлов по ρ (K задаётся бюджетом).

Считаем refine только для выбранных K тайлов.

Сборка финального pred: refined-тайлы заменяют coarse-тайлы, остальные остаются coarse.

3) Как именно считать coarse/refine (чтобы это было не “пустой if”)

Нужна имитация иерархии разрешения:

Вариант A (самый простой и достаточный)

coarse: downsample GT в H/s × W/s (например s=4) + upsample обратно до H×W (bilinear). Это имитирует “грубо”.

refine на тайле: берём GT тайл и “восстанавливаем” его точнее, чем coarse.
Практически: “refine(tile)” может просто вернуть GT_tile (идеальное уточнение) НО тогда качество станет тривиально идеальным и сравнение неинтересно.

Поэтому refinement должен быть ограниченным по мощности, например:

итеративное уточнение: pred_tile = pred_tile + α * (GT_tile - pred_tile) на n_iter шагов; каждый шаг считается “дорогим”.
Тогда refined тайл сходится к GT, но не мгновенно.
Стоимость: n_iter умножается на число refined тайлов.

Вариант B (чуть реалистичнее, но всё ещё без нейросетей)

coarse_tile: свёртка/сглаживание (Gaussian blur) + квантование, чтобы потерять края.

refine_tile: локальная “де-блюр” процедура (например unsharp mask / Laplacian sharpening) с несколькими итерациями, приближая к GT.

Разработчик выбирает A или B, но A обязателен как минимальная реализация.

4) Бюджет и метрики
4.1. Compute budget

Определяем бюджет B как число refine-операций:

B = K * n_iter, где K — число refined тайлов.

Сравнение должно идти при одинаковом B.

Сценарии:

фиксируем n_iter (например 8) и сравниваем разные K;

или фиксируем K и сравниваем разные n_iter;

минимум: один режим “фиксируем K”, чтобы ответить на вопрос.

4.2. Метрики качества

Обязательные:

Global MSE: mean((pred - GT)^2)

PSNR (из MSE)

Отдельно MSE на edge-зоне и non-edge-зоне (чтобы проверить, что маска реально ловит границы):

edge mask можно получить из GT: |∇GT| > threshold (фиксированный порог или квантиль).

Опциональные:

SSIM (если не сложно, но не обязательно).

4.3. Метрики “куда ушёл бюджет”

coverage: доля refined тайлов = K / N_tiles

overlap с edge-тайлами: сколько refined тайлов попали в edge-зоны (по GT edge mask).

распределение ρ (гистограмма/квантили) — для отчёта.

5) Экспериментальный протокол

Генерируем GT по seed.

Считаем coarse.

Baseline-dense:

выбрать режим бюджетирования:

либо “dense-with-budget”: refine ровно K тайлов, но выбрать их случайно (рандом) — честный baseline при равном K,

либо “dense-all” только для справки (как верхняя планка качества, но не равный бюджет).

Adaptive:

вычислить ρ по тайлам,

выбрать top-K,

refine их.

Сравнить метрики при одинаковом бюджете.

Запустить на наборе seeds, например 20–50 (чтобы один удачный seed не продал проект как чудо).

Выход: таблица результатов + усреднение + доверительные интервалы (хотя бы mean±std).

7) Критерии успеха/провала

Проект “жив” на уровне 0.1, если выполняется хотя бы одно:

При одинаковом бюджете B adaptive даёт стабильно (на множестве seeds) меньше MSE, чем baseline random-K (или иной равнобюджетный baseline).

При фиксированном целевом качестве (например MSE≤X) adaptive требует меньший K (или меньший B) чем baseline.

Проект “мёртв”, если:

Разница в пределах шума или adaptive хуже при равном бюджете;

Или выигрыш есть только на одном “удачном” типе поля, а на других деградирует.

8) Набор тестовых конфигов (минимум 3 сцены)

Чтобы не получилось “подогнали под один ландшафт”:

Sparse edges: 1–2 резкие фигуры на пустоте + 2 гауссианы.

Many small edges: много мелких фигур (шахматка/полосы) — проверка, что маска не умирает.

No edges: только гладкие гауссианы — adaptive должен не тратить бюджет на шум и быть не хуже.

9) Замечания, которые важно не забыть (иначе эксперимент станет клоунадой)

Baseline для сравнения при равном бюджете должен быть реально равнобюджетным. “Dense-all” — это не сравнение, это потолок.

Выбор K по top-ρ обязан быть детерминированным (tie-breaker по индексу), чтобы результаты не плясали.

Все seeds и конфиги сохранять рядом с результатами. Без этого любые цифры — художественная литература.
