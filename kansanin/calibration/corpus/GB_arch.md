# УРОВЕНЬ 1: КОНЦЕПЦИЯ

## Что это

Система автоматического управления обучением в мультиигровых оптимизациях (GAN-ы, multi-agent RL, любые N≥2 взаимодействующих функций потерь).

Состоит из двух независимых модулей, работающих на разных уровнях:

- **GravBalancer** — управляет *скоростью* обучения каждого игрока (learning rates)
- **DiversitySentinel** — управляет *направлением* обучения генератора (gradient-level diversity pressure)

## Для чего это существует

Мультиигровая оптимизация — это не минимизация одной функции. Это динамическая система, где несколько игроков с разной скоростью обучения влияют друг на друга. Основные проблемы:

1. **Дисбаланс сил** — один игрок учится быстрее другого, подавляет его, тренировка коллапсирует. Стандартное решение — ручные фиксированные пропорции LR (TTUR). Проблема: оптимальная пропорция меняется во времени.

2. **Mode collapse** — генератор находит несколько безопасных мод и перестаёт исследовать. Стандартные решения — архитектурные (minibatch discrimination) или loss-based (feature matching). Проблема: статичны, не адаптируются к текущей динамике.

## Уникальная ценность (что отличает от существующих решений)

**GravBalancer:**
- **Balance-aware дифференциальное управление.** Не "снизить общий LR когда плохо", а "обнаружить перекос между игроками и скорректировать каждого по отдельности". Этого нет в стандартных scheduler-ах.
- **N-player обобщение.** Не hardcoded "генератор vs дискриминатор", а произвольная конфигурация N≥2 игроков.
- **Самокалибровка.** Все пороги выводятся из наблюдаемой динамики во время warmup. Ноль ручной настройки под сценарий.

**DiversitySentinel:**
- **Адаптивный λ через PID.** Не фиксированный вес diversity loss, а автоматическая подстройка под текущее соотношение основного и diversity loss.
- **Двухканальная метрика.** Radial (плотность распределения) + Angular (покрытие мод) ловят разные типы коллапса.
- **Ортогональность.** Работает на уровне градиентов, не трогает LR. Не создаёт петлю обратной связи с контроллером LR.

## Архитектура: две системы

```
┌─────────────────────────────────────────────────────────────┐
│                    TRAINING LOOP                            │
│                                                             │
│  losses ──► [GravBalancer] ──► learning rates               │
│                (outer loop)     для каждого игрока          │
│                                                             │
│  samples ──► [DiversitySentinel] ──► diversity loss         │
│                (gradient level)      добавляется к loss_G   │
│                                                             │
│  Связь: однонаправленная, опциональная                      │
│  Sentinel ЧИТАЕТ состояние GravBalancer (calm mode)         │
│  GravBalancer НЕ ЗНАЕТ о Sentinel                           │
│  Proxy для GravBalancer = основной loss, БЕЗ diversity      │
└─────────────────────────────────────────────────────────────┘
```

**Контракт взаимодействия:** Sentinel добавляет diversity loss к G *до* backward(). GravBalancer получает proxy из *основного* adversarial loss (без diversity). Это предотвращает петлю: Sentinel раздувает loss G → GravBalancer думает G в стрессе → повышает LR G → усиливает нестабильность.

## Что работает, что нет (по результатам бенчмарков)

Результаты зависят от домена (2D toy vs image) и от LR. Простых ответов "работает/не работает" нет.

### 2D Toy (10×10 Gaussian grid, 100 мод, v10.7.3 sweep, 40 эпох)

```
LR        baseline    grav        div         grav_div
1e-04     73m/0.44kl  78m/0.50kl  79m/0.15kl  76m/0.21kl
5e-04     86m/1.33kl  88m/0.96kl  100m/0.02kl 100m/0.02kl
1e-03     82m/0.96kl  78m/1.33kl  97m/0.12kl  100m/0.04kl ★
2e-03     95m/0.31kl  96m/0.13kl  99m/0.06kl  99m/0.09kl
5e-03     72m/1.60kl  59m/1.67kl  93m/0.52kl  94m/0.37kl ★
1e-02     56m/2.64kl  47m/2.21kl  55m/0.79kl  56m/1.30kl
2e-02     22m/8.19kl  1m/13.6kl   1m/13.6kl   25m/7.98kl ★★
```
(★ = grav_div лучший, ★★ = единственный выживший)

**Паттерн по LR-зонам:**

**Низкий LR (1e-4 .. 2e-3):** Grav помогает умеренно (лучше KL при 2e-3), div помогает сильно. grav_div ≈ div. Система достаточно стабильна сама по себе, grav — лёгкий бонус.

**Средний LR (5e-3 .. 1e-2):** Grav один — ВРЕДИТ (59<72 мод на 5e-3, 47<56 на 1e-2). Authority ≈ 0.26 при stress ≈ 0.15 — контроллер рулит без необходимости, вносит лишнее трение. Baseline справляется сам. div один — сильно помогает с mode coverage. grav_div — синергия на 5e-3 (94 мода, лучший KL=0.37), паритет на 1e-2.

**Экстремальный LR (2e-2):** Grav один — мёртв (1 мод). Div один — мёртв (1 мод). Baseline — 22 мода с потерями. **grav_div — единственный выживший** (25 мод). Механизм: grav держит loss от взрыва → G не теряет плоскость → div имеет spread > 0 для работы → diversity loss разносит G по модам. Настоящая архитектурная синергия.

**Качественный анализ (визуально, по GIF):**
- На 5e-3: grav обеспечивает переход с 1D на 2D стратегию покрытия мод. Но ему не хватает 40 эпох — при 80 эпохах 2D-покрытие раскрывается.
- На 5e-3: div мешает grav фокусироваться на конкретных модах (антиколлапс давит на фокусировку).
- На 2e-2: grav+div — не теряют плоскость вообще; её треплет, но она держится на модах, тогда как baseline теряет и потом пытается вернуться.

**Ключевой вывод (2D toy):** Контроллер полезен на краях (низкий и экстремальный LR), вреден посередине. Корневая проблема среднего LR: authority не умеет уходить в ноль когда система здорова.

### Image domain (CIFAR-10, v10.8)

На image GAN-ах ситуация качественно другая:

- **div** — стабильно улучшает тренировку
- **grav** — steering фактически неактивен (idle fraction > 80%, deadband = max 3.5σ)
- **grav_div** — интерференция: grav не помогает, но вносит overhead и шум

**Корневая проблема image domain:** Steering работает на производной шаг-к-шагу (Δ gaps). Нестабильности image GAN — медленные дрейфы (сотни эпох), где Δ ≈ 0. Proxy signal (hinge loss) коллапсирует через ReLU в ноль, даже softplus не спасает — dynamic deadband калибруется к максимуму во время warmup, фактически отключая steering.

Climate control при этом работает (lr_meta адаптация наблюдалась), но потому что shock_ratio — его единственный живой канал. Остальные 3 канала (wall, sat, clamp) тихие из-за неактивного steering.

### Сводка: поведение по (домен × LR)

| Домен | LR-зона | grav | div | grav_div | Примечания |
|-------|---------|------|-----|----------|------------|
| 2D toy | Низкий (≤2e-3) | +слабо | ++сильно | ≈div | Grav — лёгкий бонус к KL |
| 2D toy | Средний (5e-3..1e-2) | −вредит | ++сильно | +/≈ | Grav вносит лишнее трение; grav_div = синергия на 5e-3, паритет на 1e-2 |
| 2D toy | Экстремальный (2e-2) | −−мёртв | −−мёртв | ++спасает | Единственный режим где нужны оба |
| Image | Все | −idle | ++помогает | −interference | Steering слеп к медленным дрейфам |

## Открытые вопросы

1. **Таймскейл steering для image domain.** Заменить сигнал с step-to-step derivative на что-то, что видит медленные тренды (скользящая регрессия? CUSUM? спектральный анализ?). На 2D toy steering работает — проблема не в архитектуре, а в масштабе сигнала.

2. **Authority не уходит в ноль.** На среднем LR (5e-3, 1e-2) на 2D toy, grav вредит потому что authority ≈ 0.26 при stress ≈ 0.15 — контроллер "рулит" когда не нужно. Нужен механизм полного отключения при здоровой системе (auth_min_eff пытается это решить, но недостаточно).

3. **grav + div интерференция (image domain).** Гипотеза: grav видит изменения от div-коррекций как "дисбаланс" и пытается их компенсировать — борется с div. Контракт "proxy = main loss only" должен это предотвращать, но возможна косвенная связь через изменение градиентного ландшафта.

4. **grav + div антисинергия на среднем LR (2D toy).** На 5e-3 div мешает grav фокусироваться на конкретных модах. Антиколлапс давит на фокусировку. Нужна адаптивная модуляция: при хорошем coverage — div ослабляет давление, при коллапсе — усиливает. (PID λ частично это делает, но недостаточно гранулярно.)

5. **Proxy signal design.** Hinge loss + ReLU proxy → коллапс к нулю. Softplus помогает, но deadband всё равно калибруется слишком широко. Нужен proxy, который сохраняет информативный сигнал во всём диапазоне.

6. **Бюджет эпох.** На 5e-3 и 1e-2 grav стратегии (2D покрытие) не успевают раскрыться за 40 эпох. При 80 эпохах grav находит качественно лучшую стратегию. Benchmark должен учитывать это.

# УРОВЕНЬ 2: КАРТА КОМПОНЕНТОВ

Для каждого компонента:
- **Проблема** — какую конкретную проблему решает
- **Вход → Выход** — что получает, что отдаёт (семантика, не формулы)
- **Зависит от** — какие другие компоненты нужны
- **Кто зависит от него** — кто сломается без него
- **Что будет если убрать** — конкретные последствия
- **Статус** — работает / проблемный / нужно переосмыслить

---

## GravBalancer — внутренние компоненты

### WARMUP (фазы A → B → Ramp → Active)

**Проблема:** Контроллер не может работать без калиброванных порогов. Нужно понаблюдать за системой, понять "нормальный" уровень шума, и только потом включать управление.

**Вход →** сырые proxy значения на каждом шаге.
**Выход →** калиброванные пороги: shock_snap (базовый уровень шока), noise_ref (базовый уровень шума), dyn_deadband_z_base (зона нечувствительности steering), а также плавное включение управления через ramp.

**Зависит от:** Statistics Tracking (EMA средних и волатильностей).
**Кто зависит:** ВСЕ остальные компоненты. Без warmup нет калиброванных порогов — steering, shock detection, climate реагируют на абсолютные значения, которые бессмысленны без базовой линии.
**Если убрать:** Все пороги — hardcoded defaults, система либо слишком чувствительна, либо слишком нечувствительна для конкретной задачи. Самокалибровка пропадает.
**Статус:** Работает. Единственная проблема — на hinge loss proxy сигнал может коллапсировать во время warmup, и калибровка выдаёт бесполезные пороги (deadband = max). Это проблема входного сигнала, не warmup.

---

### STATISTICS TRACKING (EMA средних, волатильностей, ref_scale)

**Проблема:** Сырые proxy-значения имеют произвольный масштаб и шумят. Нужно выделить тренд (среднее) и разброс (волатильность) для каждого игрока, плюс общую шкалу для нормализации.

**Вход →** N proxy-значений на каждом шаге.
**Выход →** per-player mus (EMA средних), sigmas (EMA волатильностей), ref_scale_ema (глобальная шкала).

**Зависит от:** Ничего (первый в пайплайне после сырых данных).
**Кто зависит:** Gaps, Shock detection, Warmup calibration — практически всё.
**Если убрать:** Ничего не работает. Это фундамент.
**Статус:** Работает, стабилен, прост.

---

### GAPS (кто в дисбалансе?)

**Проблема:** Определить, какой игрок "перетягивает" — у кого proxy выше/ниже консенсуса, нормализованно по его собственной волатильности.

**Вход →** mus, sigmas от Statistics.
**Выход →** per-player gaps (положительный = игрок "проигрывает" / в стрессе; отрицательный = "доминирует").

**Зависит от:** Statistics Tracking.
**Кто зависит:** Steering (это его основной сигнал), Calm/Shock detection (уровневые gaps для некоторых детекторов).
**Если убрать:** Steering не знает кого корректировать. Без gaps нет дифференциального управления — остаётся только глобальный LR scaling.
**Статус:** Работает. Сам по себе не является проблемой.

---

### STEERING SIGNAL (dynamic gaps → z-scores)

**Проблема:** Абсолютный уровень gaps содержит структурный сдвиг (один игрок может стабильно быть "выше" другого — это нормально). Нужно реагировать на *изменения* дисбаланса, а не на его постоянный уровень.

**Вход →** gaps (от Gaps).
**Выход →** z-scores: нормализованные, с вычтенным трендом производные gaps. Пропущенные через deadband (маленькие z → 0).

**Зависит от:** Gaps, Warmup (калибровка deadband).
**Кто зависит:** Damper/Integrator (это их вход).
**Если убрать:** Damper и Integrator работают на уровневых gaps (fallback mode). Менее чисто, но функционально.
**Статус:** ⚠️ ПРОБЛЕМНЫЙ. Это центр таймскейл-проблемы. Производная шаг-к-шагу слепа к медленным дрейфам. Dynamic deadband калибруется в максимум когда proxy коллапсирует. Этот компонент — главный кандидат на переосмысление.

---

### DAMPER (P-term)

**Проблема:** Превратить z-scores дисбаланса в корректирующее воздействие на LR. Пропорциональная реакция: больше дисбаланс → сильнее коррекция.

**Вход →** deadbanded z-scores (или level gaps).
**Выход →** per-player u_p (steering commands, ±).

**Зависит от:** Steering Signal.
**Кто зависит:** LR pipeline (u_p → ratio → LR adjustment), Authority (ограничивает u_cap), Calm (может обнулить u_p).
**Если убрать:** Нет пропорциональной коррекции. Остаётся только integrator (медленный, без immediate response). Система теряет быструю реакцию.
**Статус:** Механизм работает. Проблема — вход (steering signal), а не сам damper.

---

### INTEGRATOR (I-term)

**Проблема:** Damper реагирует только на текущий дисбаланс. Если дисбаланс мал но постоянен, damper даёт слишком слабую коррекцию. Integrator накапливает постоянное смещение.

**Вход →** deadbanded gaps (те же, что у damper).
**Выход →** per-player u_i (накопленная коррекция). Zero-sum проекция: сумма u_i = 0 всегда.

**Зависит от:** Steering Signal, Auto-gating (может быть отключён).
**Кто зависит:** LR pipeline (u_i + u_p → u_total).
**Если убрать:** Нет коррекции постоянных смещений. Для быстро меняющихся систем — не критично. Для медленных дрейфов — потенциально важен, но только если steering signal вообще видит этот дрейф.
**Статус:** Механизм корректен. На практике часто отключён auto-gating-ом из-за шумных сигналов. Потенциально мог бы быть ключом к решению проблемы медленных дрейфов (если подать ему правильный сигнал).

---

### CALM / SHOCK DETECTION

**Проблема:** Иногда система получает сильный удар (shock) или начинает осциллировать (mechanical overshoot). В этот момент steering должен остановиться, а не усугублять ситуацию.

**Вход →** resid (отклонение от среднего), shock_thr (калиброван из warmup), mechanical risk (из predictor).
**Выход →** calm mode (обнулить steering), shock path (BYPASS/SUSTAINED/NORMAL), distress level.

**Зависит от:** Statistics, Warmup (shock_thr).
**Кто зависит:** Steering (calm обнуляет u_p, u_i), Climate (shock_ratio входит в E), DiversitySentinel (опционально снижает λ при calm).
**Если убрать:** Steering продолжает работать во время шоков — усугубляет нестабильность. Это как убрать ABS: на сухой дороге незаметно, на мокрой — вылет.
**Статус:** Работает. Проблема: без рабочего steering — защищает тишину от тишины.

---

### AUTHORITY (Layer 1)

**Проблема:** В шумной среде steering'у нельзя давать полный диапазон — он будет реагировать на шум. Нужно адаптивно сужать диапазон при высоком шуме.

**Вход →** noise_norm (текущий уровень шума, нормализованный к noise_ref из warmup).
**Выход →** authority_factor (множитель для u_cap, 0..1). Чем шумнее — тем меньше authority.

**Зависит от:** Warmup (noise_ref), Statistics.
**Кто зависит:** Steering (u_cap_eff = u_cap × authority × ramp).
**Если убрать:** Steering реагирует на шум как на сигнал. Особенно опасно при высоком N (много шумовых каналов).
**Статус:** Работает.

---

### CONTROL STRESS (Authority squeeze)

**Проблема:** Authority реагирует на мгновенный шум. Но бывает хронический стресс — система постоянно на грани (частые wall hits, частые hold). Нужен медленный накопитель стресса, который постепенно сжимает authority.

**Вход →** wall events, hold events, saturation events (от steering и governor).
**Выход →** stress_auth_factor (дополнительный множитель authority, медленнее чем Authority).

**Зависит от:** Steering, Governor (сигналы wall/hold/sat).
**Кто зависит:** Authority (перемножаются).
**Если убрать:** Authority реагирует только на мгновенный шум, не на хроническую перегрузку. При длительном стрессе steering остаётся слишком агрессивным.
**Статус:** Работает как механизм. На практике малозаметен, потому что steering итак молчит на image tasks.

---

### TRIPWIRE (Layer 1.5)

**Проблема:** Между мягким Authority squeeze и тяжёлым Panic есть пробел. Нужна короткая быстрая реакция (10 шагов) на устойчивый шок, без полной паники.

**Вход →** sustained shock signals, legacy calm triggers.
**Выход →** trip_active (кратковременный authority × 0.5 + cooldown).

**Зависит от:** Shock detection.
**Кто зависит:** Authority (перемножаются).
**Если убрать:** Система прыгает от "мягкий squeeze" к "полная паника" без промежуточной реакции. Может вызвать избыточные panic-и.
**Статус:** Работает.

---

### PANIC (Layer 2)

**Проблема:** Системная потеря контроля — когда steering, authority, tripwire не справляются. Нужен последний рубеж: снижение *базового* LR (а не steering range).

**Вход →** compound symptom score из 4 каналов: wall rate, shock stress, flip rate, hold rate, clamp rate. Всё дробное (mean-of-players), N-инвариантное.
**Выход →** panic_factor (множитель для base_lr, 0.3..1.0). Требует 20 последовательных тиков подтверждения.

**Зависит от:** Steering signals (wall, saturation, hold, clamp, flip).
**Кто зависит:** LR pipeline (lrs_raw = base_lr × panic_factor × ...).
**Если убрать:** При системном разладе LR не снижается. Climate может частично компенсировать (тоже снижает effective LR), но медленнее и через другой механизм.
**Статус:** Работает. Активируется редко (by design). 3 из 4 входных каналов зависят от steering — без рабочего steering panic тоже слепнет.

---

### CLIMATE CONTROL (Layer 3)

**Проблема:** Самый внешний уровень защиты. Когда *общая энергия системы* зашкаливает (не дисбаланс, а абсолютный уровень стресса), нужно снизить effective LR глобально. Также anti-chatter: при быстрых спайках энергии — заморозить steering на 1 шаг.

**Вход →** E = max(shock_ratio, 1+wall_rate, 1+u_sat_frac, 1+clamp_frac). Четыре канала, из которых wall_rate, u_sat_frac, clamp_frac — от steering.
**Выход →** lr_meta (глобальный множитель effective LR, 0.01..1.0), hold (заморозить steering на следующий шаг).

**Зависит от:** Shock detection (shock_ratio), Steering (wall, sat, clamp сигналы), Control Stress (wall_rate_ema).
**Кто зависит:** LR pipeline (финальный множитель: lrs_eff = lrs_final × lr_meta).
**Если убрать:** Нет глобальной защиты от перегрева. При слишком высоком base_lr система может разлетаться медленно, и ни один внутренний компонент это не поймает (steering корректирует *баланс*, а не *абсолютный уровень*).
**Статус:** ⚠️ ДВОЙСТВЕННЫЙ. Механизм работает и реально снижает lr_meta на бенчмарках. Но 3 из 4 входных каналов — от steering. Без рабочего steering, climate видит только shock_ratio. По сути вырождается в "reduce LR if shock is high" — банально, но полезно.

---

### RATE GOVERNOR

**Проблема:** Даже корректное steering-решение не должно менять LR слишком резко за один шаг — это создаёт скачки в градиентном поле.

**Вход →** proposed LR change (от steering + panic).
**Выход →** clamped LR change (max_jump_up, max_jump_down). Адаптивно: в шумных средах — жёстче.

**Зависит от:** Noise_norm (от Statistics).
**Кто зависит:** LR pipeline. Также генерирует hold_lr сигнал, который идёт в: Integrator anti-windup, Panic scoring, Control Stress.
**Если убрать:** LR может прыгать резко. Downstream: hold_lr сигнал пропадает, panic и stress теряют канал.
**Статус:** Работает. Простой и надёжный.

---

### COMFORT THROTTLE

**Проблема:** Когда система долго спокойна, текущий LR может быть субоптимально низким (из-за предыдущих снижений). Нужен механизм мягкого восстановления.

**Вход →** calm duration, wall rate, shock state, saturation — много gate conditions.
**Выход →** comfort_factor (≥1.0, boost).

**Зависит от:** Shock, Steering (sat/wall/hold flags).
**Кто зависит:** LR pipeline (lrs_final = lrs_gov × comfort_factor).
**Если убрать:** LR после снижений восстанавливается только через steering (медленно) или climate relaxation (очень медленно). Система становится консервативнее, чем нужно.
**Статус:** Работает. Вторичный компонент — если steering и climate исправны, comfort — nice to have.

---

### RATIO CLAMP

**Проблема:** Жёсткий контракт: никакой игрок не может иметь LR больше чем max_ratio × другой. Гарантия того, что steering не создаёт катастрофических перекосов.

**Вход →** proposed per-player LRs.
**Выход →** clamped LRs, clamp_frac (доля зажатых игроков — идёт в Panic и Climate).

**Зависит от:** Steering output (через LR pipeline).
**Кто зависит:** Panic (clamp_frac как канал), Climate (clamp_frac как канал).
**Если убрать:** Steering теоретически может выставить LR одного игрока в 100× от другого. На практике governor ограничивает jump, так что ratio растёт постепенно, но без clamp — потолка нет.
**Статус:** Работает. Простой, необходимый.

---

## DiversitySentinel — внутренние компоненты

### PROJECTOR (Feature Extraction)

**Проблема:** Сравнивать raw pixels бессмысленно для distribution matching. Нужна фиксированная проекция в feature space.

**Вход →** raw generated/real samples (тензоры).
**Выход →** flat feature vectors.

**Зависит от:** Ничего.
**Кто зависит:** Radial и Sliced Wasserstein.
**Если убрать:** Distribution comparison на raw pixels. Для 2D toy data — ОК (nn.Identity). Для изображений — непрактично.
**Статус:** Работает. Frozen (не учится) — by design.

---

### RADIAL WASSERSTEIN (density spread)

**Проблема:** Генератор может коллапсировать в точку или оболочку (все сэмплы на одном расстоянии от центра).

**Вход →** centered features (fake & real).
**Выход →** scalar loss: насколько радиальные распределения различаются.

**Зависит от:** Projector, Center EMA.
**Кто зависит:** Match error (weighted sum с Angular).
**Если убрать:** Потеря чувствительности к point/shell collapse. Angular coverage может это частично поймать, но менее точно.
**Статус:** Работает.

---

### SLICED WASSERSTEIN (angular coverage)

**Проблема:** Генератор может покрывать правильный радиус, но только в нескольких направлениях (кластеризация мод).

**Вход →** centered features (fake & real), random projection directions.
**Выход →** scalar loss: насколько проекции на случайные направления различаются.

**Зависит от:** Projector, Center EMA.
**Кто зависит:** Match error.
**Если убрать:** Потеря чувствительности к mode clustering. Radial может частично компенсировать.
**Статус:** Работает.

---

### PID CONTROLLER ДЛЯ λ

**Проблема:** Фиксированный λ для diversity loss — либо слишком слабый (не мешает коллапсу), либо слишком сильный (подавляет adversarial learning). Нужна автоподстройка.

**Вход →** loss_G_main, diversity_loss (их соотношение vs target_ratio).
**Выход →** raw λ (в log-space).

**Зависит от:** Radial + Sliced → match_error → diversity_loss. Основной loss генератора.
**Кто зависит:** Lambda Governor.
**Если убрать:** λ = const. Работает, но деградирует при смене режимов обучения.
**Статус:** Работает. P-only controller (без I и D) — достаточен, λ и так persistent.

---

### LAMBDA GOVERNOR (rate limiter)

**Проблема:** PID может выдать резкий скачок λ, что с точки зрения GravBalancer (если используется) выглядит как shock. Нужен rate limiter.

**Вход →** raw λ от PID.
**Выход →** governed λ (max ±15%/step, + EMA smoothing).

**Зависит от:** PID.
**Кто зависит:** Финальный λ_div → diversity loss computation.
**Если убрать:** Скачки λ. Без GravBalancer — терпимо. С GravBalancer — может вызывать ложные shock-и.
**Статус:** Работает.

# ПЕТЛИ ОБРАТНОЙ СВЯЗИ И МЕХАНИЗМЫ СТАБИЛИЗАЦИИ

GravBalancer — не pipeline модулей, а **иерархическая система управления** с тремя вложенными петлями обратной связи, работающими на разных временных масштабах.

Без понимания этих петель невозможно предсказать поведение системы при изменениях.

## Три контура

```
Steering   (быстрый, ~10 шагов)    imbalance → steering → LR → imbalance
Authority  (средний, ~100 шагов)    noise → authority → сила steering → noise
Climate    (медленный, ~1000 шагов) LR → турбулентность → E metric → lr_meta → LR
```

## Петля 1: Steering (PID-контур)

```
gaps → steering (P + I) → u_total → LR → player dynamics → new gaps
```

Это основной управляющий контур. Классический риск — **integrator wind-up**: ошибка не уменьшается (ratio clamp блокирует LR), интегратор копит управление, clamp отпускает → гигантский выброс LR.

**Разрыватели:**

Anti-windup Variant C (три предохранителя):
- governor hold / ratio clamp активны → `delta_i = 0` (полная заморозка)
- `|u_total| ≈ u_cap` → блокируются только компоненты, толкающие дальше в saturation; уменьшающие — разрешены
- `delta_i -= mean(delta_i)` — zero-sum projection убирает перекосы между игроками

Результат: интегратор не может разогнаться, пока стена активна.

## Петля 2: Authority (adaptive gain)

```
noise_norm → authority squeeze → u_cap_eff → сила steering → LR changes → system dynamics → noise_norm
```

Менее очевидная, но более коварная. Если authority слишком сильно душит steering → контроллер не корректирует дисбаланс → игроки расходятся → шум растёт → authority душит ещё сильнее. Positive feedback → паралич контроллера.

**Разрыватели:**

- **Deadband**: steering реагирует только на `z > deadband`. Мелкий шум игнорируется, не запускает адаптивный каскад.
- **Quiet gate**: steering уменьшается плавно (smoothstep), не ступенчато. Нет резкого перехода "работает / не работает".
- **Dynamic authority floor**: `auth_min_eff = f(max(stress, intervention_rate))`. Authority не может уйти в ноль — если система реально страдает (высокий stress или частые интервенции), authority возвращается.
- **Noise_ref refractory**: во время calm/shock `noise_ref` обновляется в `refractory_div` раз медленнее. Предотвращает дрейф порогов пока контроллер парализован.

## Петля 3: Climate (внешний мета-контроллер)

```
LR → system behaviour → E metric → E_fast/E_slow → lr_meta → LR
```

Медленная петля. Если бы `lr_meta` реагировал быстро — система бы осциллировала между "LR слишком высокий → climate давит → LR слишком низкий → climate отпускает → ..."

**Разрыватели:**

- **Dual EMA**: E_fast (τ ≈ 30) ловит спайки для hold, E_slow (τ ≈ 1000) управляет lr_meta. lr_meta реагирует только на хронические проблемы.
- **Asymmetric slew**: tighten fast, relax slow. Система быстро реагирует на опасность, но медленно возвращается — overdamped response.
- **Hold hysteresis**: E_fast spike → hold с гистерезисом (разные пороги on/off). Предотвращает чатер.

## Сводка

| Петля | Роль | Временной масштаб | Тип риска | Разрыватели |
|-------|------|------------------|-----------|-------------|
| Steering | баланс игроков | ~10 шагов | integrator wind-up | anti-windup Variant C |
| Authority | адаптивный gain | ~100 шагов | gain instability / паралич | deadband, quiet gate, authority floor, noise_ref refractory |
| Climate | предотвращение штормов | ~1000 шагов | slow oscillation | dual EMA, asymmetric slew, hold hysteresis |

## Архитектурный принцип

Три петли образуют иерархию вложенных регуляторов:

```
PID steering (быстрый)
  внутри authority governor (средний)
    внутри climate meta-controller (медленный)
```

Такие конструкции (control system controlling another control system) склонны к автоколебаниям. Стабильность здесь обеспечивается за счёт deadband-ов, гистерезисов и асимметричных EMA на каждом уровне — стандартный набор инструментов борьбы с автоколебаниями в многоуровневых системах управления.

## Cross-system петля (DiversitySentinel ↔ GravBalancer)

DiversitySentinel меняет градиенты G → main loss G меняется → proxy для GravBalancer меняется. Контракт (proxy = main loss only, без diversity) разрывает прямую связь, но косвенно main loss тоже реагирует на diversity pressure.

Координация однонаправленная: GravBalancer → DiversitySentinel (distress_level), не наоборот. DiversitySentinel не знает о GravBalancer напрямую.

## Warmup как точка хрупкости

Все пороги калибруются из warmup. Если warmup получил нерепрезентативные данные (collapsed proxy, аномальный loss), вся система работает на плохих порогах. Convergence-based warmup (phase B) и degraded mode частично это парируют, но не гарантируют.

# АРХИТЕКТУРНЫЕ ИНВАРИАНТЫ

Правила, нарушение которых ломает separation of concerns. Должны проверяться при любом изменении.

**Разделение ΔLR и LR magnitude:**
- Steering/Authority/Comfort управляют **соотношением** LR между игроками (ΔLR). Они никогда не трогают base_lr.
- Panic/Climate управляют **абсолютной величиной** LR (magnitude). Они никогда не трогают steering напрямую.

Пока это разделение соблюдается, два контура не могут создать алгебраическую петлю. Climate может обнулить steering через hold — но это одношаговый gate, не постоянное вмешательство в steering-логику.

**Контракт DiversitySentinel:**
- Proxy для GravBalancer = main adversarial loss, БЕЗ diversity loss. Нарушение создаёт петлю: Sentinel раздувает loss G → GravBalancer думает G в стрессе → повышает LR G → усиливает нестабильность.
- Sentinel ЧИТАЕТ состояние GravBalancer (distress_level), GravBalancer НЕ ЗНАЕТ о Sentinel.

**Слои не перескакивают:**
- Authority не трогает base_lr (только u_cap)
- Climate не трогает steering (только lr_meta, и hold как gate)
- Panic не трогает authority (только base_lr multiplier)

# КАРТА ОТВЕТСТВЕННОСТИ

Быстрая таблица для дебага: "система ведёт себя странно → какой блок виноват?"

| Блок | Отвечает за | НЕ отвечает за |
|------|-------------|----------------|
| Steering (P+I) | баланс между игроками | абсолютный уровень LR |
| Authority | ограничение силы управления при шуме | обнаружение аномалий |
| Control Stress | обнаружение хронической перегрузки контроллера | прямое управление LR |
| Tripwire | быстрая реакция на шоки (10-step intervention) | длительное подавление (это делает Panic) |
| Panic | аварийное снижение base_lr при системной потере контроля | тонкую настройку баланса (это делает Steering) |
| Climate | регулирование глобальной энергии LR (lr_meta) | реакцию на одиночные спайки (это делает Calm) |
| Calm | аварийная остановка steering при шоках/mech risk | долгосрочную адаптацию (это делает Climate) |
| Comfort | ускорение в спокойные периоды (boost ≥ 1) | работу в stress-режиме (gates off) |
| Warmup | калибровка всех порогов из наблюдений | управление в active phase |
| DiversitySentinel | сохранение разнообразия мод через gradient pressure | управление скоростью обучения |

**Правило дебага:** если LR всех игроков слишком низкий — смотри Climate/Panic. Если один игрок подавлен другим — смотри Steering/Authority. Если система осциллирует — смотри Calm/Predictor/Flip. Если steering "мёртвый" (idle >80%) — смотри deadband/quiet-gate/authority floor.

# КЛЮЧЕВЫЕ СИГНАЛЫ

Семантика сигналов, неочевидных из имени. **Правило включения:** сигнал попадает в эту таблицу только если его семантика НЕ очевидна из имени ИЛИ его численный диапазон критичен для интерпретации. Остальное — в графе зависимостей.

| Сигнал | Источник | Семантика | Диапазон |
|--------|----------|-----------|----------|
| gaps | Gaps | нормированный дисбаланс: (μᵢ − consensus) / σᵢ | ≈ [-3, 3] |
| noise_norm | Gaps → Auth | текущий шум / эталонный шум (из noise_ref) | [0, ∞), 1.0 = "нормально" |
| authority_factor | Auth | разрешённая сила steering, 1=полная, 0=запрещена | [auth_min_eff, 1.0] |
| u_sat_frac | U_total | доля игроков, чей steering упёрся в u_cap | [0, 1], N-инвариант |
| wall_or_shock | Panic internal | max(wall_score, shock_stress_ema) — strongest distress | [0, 1] |
| E (energy) | Climate | max(shock_ratio, 1+wall_rate, 1+u_sat, 1+clamp) — storm metric | [1, ∞), 1=штиль |
| lr_meta | Climate | глобальный множитель LR, 1=норма, <1=climate давит | [floor, 1.0] |
| world_drift | Signal | shock_ema / shock_snap — насколько мир шумнее warmup | [0, ∞), 1.0 = как при калибровке |
| distress_level | GB → DS | 0=норма, 1=trip, 2=calm/panic — уровень кризиса GB | {0, 1, 2} |

# КАК ИСПОЛЬЗОВАТЬ ЭТУ КАРТУ

**Перед любым изменением:**
1. Найти компонент, который меняешь
2. Проверить "Кто зависит от него" — убедиться, что зависимые компоненты не сломаются
3. Проверить "Зависит от" — убедиться, что входные данные всё ещё поступают
4. Проверить раздел "Ключевые петли" — убедиться, что не создаёшь новую положительную обратную связь

**Перед любым удалением:**
1. Проверить "Что будет если убрать"
2. Проверить, не теряют ли downstream компоненты свои входные каналы
3. Особенно: Panic и Climate теряют большую часть входов без steering

**При добавлении нового компонента:**
1. Определить его место в pipeline (строгий порядок!)
2. Определить входы/выходы в формате этой карты
3. Проверить, не создаёт ли он новую петлю обратной связи
